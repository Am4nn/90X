# 90X build plan: Part 1 (data pipeline) + Part 2 (foundation + Library)

## Context

`.planning/SPEC.md` is approved. Raw data (42 sources, 17.4 GB) is in `.data/`, every service in `web/.env.local` is verified live, and the repo has a scaffold: `web/` (Next.js 16, Supabase SSR clients, Drizzle config, AI SDK provider in `web/src/lib/ai.ts`), `pipeline/` (uv, downloader in `pipeline/src/pipeline/`), `supabase/` (config with Google enabled, no migrations yet).

This plan turns the spec's first two parts into working software: the content the app needs (problems, notes, topics, knowledge chunks, draft cards) and the app shell you can sign into, browse and check in from. Parts 3–5 get their own plans later.

## Build order

The pipeline writes into Supabase tables, so the shared schema comes first.

| Stage | What | Done when |
|---|---|---|
| A | Content + access schema (migrations) | Tables exist in Supabase with RLS |
| B | Part 1: pipeline | Supabase holds problems, topics, documents; Vector holds chunks; draft cards exist |
| C | Part 2: app foundation + Library | Sign in → approved → setup → browse Library → check in → LeetCode sync |

Each stage ends with a commit and push. Plans are saved to `.planning/plans/` when execution starts.

## Stage A: schema

Migrations in `supabase/migrations/`, applied with `bun run db:push` (uses `SUPABASE_ACCESS_TOKEN`, `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`), then `bun run db:pull` (Drizzle types into `web/src/db/pulled`) and `bun run db:types` (supabase-js types).

- `0001_access.sql`: `profiles` (user_id → auth.users, name, avatar, role, language, timezone, leetcode_username, notification prefs), `user_approvals` (Curfew's shape from `../curfew/migrations/0002_app.sql`: status pending/approved/rejected, is_admin, requested_at, decided_at, decided_by, same CHECK). Trigger on `auth.users` insert creates both rows (pending). SQL helpers `is_approved()` and `is_admin()` (security definer, `auth.uid()`).
- `0002_content.sql`: `sources`, `topics`, `topic_links`, `problems`, `documents`, `card_batches`, `cards` exactly as spec §5.1. RLS: select for `is_approved()` users; cards only `status = 'live'` (admins see drafts); no insert/update policies (pipeline writes with the direct connection).
- `0003_checkins.sql`: `checkins` (spec §5.2 incl. attempts, minutes_suggested, external_id, unique on user+external_id), `integration_status`, view `checkins_public` (all columns except `note`). RLS: owner full access; approved users read the view.
- Tables for parts 3–5 (campaigns, missions, card_reviews, coach_*, …) are added in their own plans, not now.
- `web/src/db/schema.ts` re-exports the pulled schema.

## Stage B: Part 1, data pipeline

All code in `pipeline/src/pipeline/`, extending the existing CLI in `__init__.py`, `config.py` (paths, dotenv) and `sources.py` (roles). New deps: `duckdb`, `pydantic`, `pypdf`, `rapidfuzz`, `pytest`. Everything lands first in `.data/staging.duckdb`, the master copy.

### B1. Foundations
- `staging.py`: DuckDB connection + DDL mirroring the Supabase content tables, plus `llm_calls` (model, tokens, cost, purpose) and `chunks`.
- `llm.py`: `openai` client from `AI_BASE_URL`/`AI_API_KEY`; `complete_json(prompt, schema: pydantic model, model=fast|smart)` with JSON mode, schema validation, one retry, cost logging; `is_off_peak()` (DeepSeek off-peak window) and a `--wait-off-peak` flag for big runs.
- `pipeline/.env` gets the AI and DB values already verified in `web/.env.local`.

### B2. DSA normalize (`normalize/dsa.py`)
Join on LeetCode slug:
- Base: `dsa/leetcode-dataset` (newfacade; `task_id` = slug, question_id, difficulty, tags, problem_description, completion = Python solution, input_output).
- `dsa/leetcode-multilang` (greengerong): Java, C++, JS solutions (strip ``` fences).
- `dsa/leetcode-detailed` (kaysss CSV): acRate, totalAccepted, similarQuestions, topicTags, category.
- `dsa/neetcode/.problemSiteData.json`: pattern, neetcode150, blind75, video id, link slug.
- `dsa/company-wise-liquidslr/<Company>/5. All.csv`: frequency per company (slug from `Link`). Other company repos are ignored (redundant).
Output: `problems` rows with `kind='leetcode'`, `solutions` as {language: code}, `companies` as {company: frequency}.

### B3. Competitive subset (`normalize/competitive.py`)
Stream only statement/solution/metadata columns from `.data/competitive/*` (never the test columns). Pre-filter by length and source, then triage "interview-like?" with DeepSeek Flash on ~2,000 candidates → keep ~300. Laya experiment is a separate optional command (`pipeline laya-eval`) run on 200 hand-labeled rows; not on the critical path.

### B4. Documents (`normalize/docs.py`)
Markdown split by `##`/`###` headings into `documents` (title, body_md, url to the source file on GitHub, domain):
- System design: primer README + `solutions/system_design/*`, karan `README.md` (551 headings).
- CS: `last-minute-notes/*.md`, `cs-fundamentals-interview/{OS_COA,DBMS,CN,OOPS}`, devops-exercises `topics/{linux,os,databases,dns,sql}`.
- Java: `java-basics/*.md`, `java-interview-guide`, `java-interview-devinterview`. SQL: `sql-basics/*.md`.
- OSTEP: 68 PDFs via `pypdf`, one document per chapter section.
- LLD, AI and behavioral sources are loaded the same way for the Library (role `reference`), no cards.

### B5. Enrich (`enrich/`)
- `patterns.py`: NeetCode pattern where available; otherwise DeepSeek Flash picks one of the 18 NeetCode patterns from statement + solution. Writes `.data/review/pattern_sample.csv` (50 random rows) for a hand check.
- `importance.py`: score 0–1 = NC150/Blind75 boost, then max company frequency, then log(totalAccepted).
- `topics.py`: DSA topic tree = the 18 NeetCode patterns + fixed roadmap edges (for the Pattern Map). Other domains: DeepSeek drafts a topic list from document headings into `pipeline/topics/<domain>.yaml` (name, slug, importance, parent). **You approve these files** (edit + commit); then documents are classified into approved topics.

### B6. Chunks → Upstash Vector (`chunk.py`, `vector.py`)
300–500-word chunks from documents and problem statements; id = `doc:<id>:<n>` or `prob:<slug>:<n>`; `data` = text; metadata = kind, topic, source, title, url. Upsert via REST (`UPSTASH_VECTOR_REST_URL/TOKEN`, index embeds with text-embedding-3-small). Content hash stored in staging so re-runs only send changed chunks.

### B7. Cards (`cards/`)
- `generate.py`: per topic batch, grounded in a source passage; formats typed / flash / mcq / output (bug later); pydantic schema per format (prompt, answer, key_points 2–4, options, source_refs, difficulty). Scope: problems with importance ≥ threshold (NC150, Blind75, top company-frequency, ~600) + approved topics of system design, CS, Java, SQL.
- `check.py`: second pass scores correctness vs source, clarity, interview relevance (1–5); drop below bar; dedupe with rapidfuzz on normalized prompts within a topic.
- Batch metadata in `card_batches` (ai_pass_rate).

### B8. Publish (`publish.py`)
Upsert `sources, topics, topic_links, problems, documents` and new `card_batches/cards` (status `draft`) into Supabase over `DATABASE_URL` from `pipeline/.env` (session connection), in one transaction per table, idempotent on natural keys (slug, source+path).

### B9. CLI + tests
Commands: `normalize [dsa|competitive|docs]`, `enrich`, `topics draft|apply`, `chunk`, `embed`, `cards generate|check`, `publish`, `status` (row counts, LLM spend). `pytest` fixtures with 5–10 real rows per source for normalize/join/importance/chunk/card-schema; LLM calls mocked.

## Stage C: Part 2, foundation + Library

### C1. Design system + shell
- `web/src/app/globals.css`: Tailwind v4 `@theme` tokens from spec §7 (colours, six type styles), dark only; shadcn theme variables mapped to them.
- Fonts via `next/font/google`: Sora, Manrope (drop Geist).
- Route group `web/src/app/(app)/` with layout: bottom tab bar (mobile) / 220px sidebar (desktop), icons inline SVG as in `.planning/mockups/`. Pages: `today`, `feed`, `library`, `coach`, `me` (Today/Feed/Coach are placeholders until parts 3–5).
- Reuse from Curfew where it fits: PWA manifest pattern (`../curfew/src/app/manifest.ts`), icons, `public/sw.js` basics.

### C2. Auth + approval (Curfew-style)
- `web/src/proxy.ts` (Next 16's middleware) refreshes the Supabase session (check `node_modules/next/dist/docs` for the proxy API first).
- `/sign-in` (Google button, `signInWithOAuth`), `/auth/callback` route (code exchange), `/pending` waiting screen.
- `(app)/layout.tsx` gate: no session → `/sign-in`; not approved → `/pending`.
- `/admin/users`: list pending/approved/rejected, approve/reject (server action, `is_admin()` checked).
- `web/scripts/admin-grant.ts` + `bun run admin:grant <email>`: sets approved + is_admin over `DIRECT_URL`.

### C3. Setup
First-run flow after approval: name, target role, DSA language, timezone, campaign length (30/60/90/custom), LeetCode username (optional). Stored in `profiles` (campaign + templates arrive in part 3; the diagnostic in part 4).

### C4. Library
- `library/page.tsx`: domain tabs (DSA, Design, CS, Java, SQL, LLD, AI, Competitive); search (Postgres ilike on title).
- DSA: Pattern Map component (SVG from `topics` + `topic_links`, node state from the user's check-ins: mastered / in progress / weakest pulses), problem table per pattern (level, companies, status), sorted by importance.
- Problem page `library/problem/[slug]`: statement (markdown), solution in the user's language (collapsed), NeetCode video link, LeetCode link, friend's check-in line, check-in panel (desktop) / sheet (mobile).
- Topic + document reader `library/topic/[slug]` with `react-markdown`, source link.
- Data access: server components with Drizzle (`web/src/db/index.ts`) for content; supabase-js under RLS for user data.

### C5. Check-ins
Server action `checkIn({problemId, result, minutes, note})` → `checkins`; mission ticking arrives in part 3. Friends' activity reads `checkins_public`.

### C6. LeetCode integration (pluggable, spec §6.6)
- `web/src/lib/activity/source.ts`: `ProblemActivitySource` interface; `leetcode.ts` adapter (GraphQL `recentSubmissionList`, `userProfileUserQuestionProgressV2`, direct from server).
- `web/src/lib/activity/sync.ts` (pure, unit-tested): group submissions by problem → result + attempts + suggested minutes (capped 2 h); create missing check-ins (source `leetcode_sync`, external_id), update `integration_status` (3 failures → unavailable, back off to daily).
- Triggers: Sync button, on app open (Redis `90x:lcsync:<user>` throttle 15 min, via `@upstash/redis`), QStash schedule `90x-leetcode-sync` every 6 h → `/api/jobs/leetcode-sync` verifying the signature with URL (`@upstash/qstash` Receiver).
- Confirm list UI after sync (adjust result/time chips). `LEETCODE_SYNC_ENABLED` + missing username hide everything.
- Me page: LeetCode totals card.

### C7. Env + deps
`web/src/lib/env.ts` validates env with Zod at startup (server vs `NEXT_PUBLIC_*`). New deps: `@upstash/redis`, `@upstash/qstash`, `react-markdown`, `remark-gfm`, `@sentry/nextjs` (wired minimal now).

- **Stage A:** `bun run db:push` succeeds; `bun run db:pull` and `db:types` generate files; `bun run typecheck` passes. RLS test script: a pending user reads 0 content rows; an approved user reads content but not another user's check-in notes.
- **Stage B:** `uv run pytest` green. `uv run pipeline status` shows ~2.6K problems (all with pattern and importance), ~300 competitive, documents per domain, topic files approved, chunk count matching Vector `/info`, draft cards per domain with pass rates, total LLM spend (expected a few dollars). Spot checks: `.data/review/pattern_sample.csv` ≥ 90% correct; a Vector `query-data` for "consistent hashing" returns the Primer section; 20 random cards read sensibly.
- **Stage C:** `bun run typecheck`, `lint`, `test` (Vitest: sync grouping, suggested time, importance sort) and `build` pass. Manual run (`bun run dev`): sign in with Google → pending screen → `bun run admin:grant` → approved → setup → Library shows the Pattern Map and NeetCode-ordered problems → open a problem, check in → friend view shows it without the note → set LeetCode username, press Sync → recent solves appear with suggested times → QStash schedule visible as `90x-leetcode-sync`.
